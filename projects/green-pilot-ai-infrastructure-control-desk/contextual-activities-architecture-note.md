# Architecture Note — Контекстные режимы и sovereign control desk

> Инициатива: Green Pilot — Контрольный контур AI-инфраструктуры  
> Состояние артефакта: Черновик  
> Classification: Green  
> Дата: 2026-09-20  
> Связанный Gate: Gate 1 — Revision  
> Статус решения: Требуется review владельца

## 1. Цель заметки

Зафиксировать целевую архитектурную идею для будущего локального Control Desk:
система должна помогать владельцу работать в разных контекстах, не передавая
владение данными, решениями и полномочиями внешнему AI-поставщику.

Это исследовательский Markdown-артефакт. Он не создаёт UI, исполняемый код,
автоматизацию, API-интеграцию, облачную синхронизацию или системные изменения.

## 2. Источник идеи

Внешний архитектурный ориентир: концепция Kadai для KDE Plasma. Она предлагает
рассматривать AI как инфраструктурный слой с отдельными Activities, явными
разрешениями, декларативным согласованием состояния и контролем пользователя
над персональной моделью.

`Fact:` Kadai на момент создания этой заметки является концепцией для
обсуждения, а не опубликованным рабочим продуктом.

`Decision:` Использовать Kadai только как источник принципов. Не копировать
его как техническую реализацию и не предполагать наличие готовых компонентов.

## 3. Архитектурная гипотеза

`Assumption:` Для personal AI infrastructure полезнее разделять работу не по
модели или приложению, а по явно выбранному контексту деятельности.

В будущем Control Desk может хранить декларативное состояние инициативы и
показывать его владельцу через контекстные режимы. Агент или модель не должны
самостоятельно выбирать режим, менять его или расширять свои полномочия.

```text
Владелец выбирает Activity
        ↓
Control Desk определяет разрешённые данные и действия
        ↓
Frigga определяет текущий Gate и нужный артефакт
        ↓
AI готовит только разрешённый Draft
        ↓
Владелец review / approve / reject
        ↓
Состояние и evidence фиксируются декларативно
```

## 4. Предлагаемые Activities

| Activity | Цель | Артефакты | Агент может | Без отдельного approval нельзя |
|---|---|---|---|---|
| Governance | Rules, Gates, решения и audit trail | Rules, decisions, Gate packs | Читать, анализировать, готовить Draft | Менять правила, утверждать решения, выполнять внешние действия |
| Discovery | Исследование проблемы и evidence | Research brief, hypotheses, evidence register | Формулировать вопросы, сравнивать варианты | Отправлять Yellow/Red data, выполнять внешний research без approval |
| Planning | Baseline, roadmap и delivery outline | Passport, milestones, RAID-ED | Готовить Draft плана | Принимать обязательства или фиксировать сроки как утверждённые |
| Delivery | Утверждённые обратимые задачи | Approved task, diff, evidence, status | Готовить diff и выполнять разрешённые действия | Deploy, purchase, push, merge, delete, change access, external call |
| Review | Проверка результата и lessons learned | Status, acceptance evidence, Gate pack | Сопоставлять результат с baseline | Объявлять результат approved без решения владельца |
| Research | Работа с внешними источниками | Research packet, citations, source log | Готовить search plan и evidence summary | Передавать чувствительный контекст или выдавать поиск за решение |

## 5. Декларативное состояние

Для будущей control-модели достаточно начинать с малого набора читаемых полей:

```text
initiative_id
initiative_name
activity
current_gate
artifact_state
data_class
overall_status
confidence
decision_owner
next_decision
next_review_trigger
open_raid_ed_count
evidence_status
```

`Assumption:` Эти поля достаточны для первой версии декларативной модели.

`Evidence gap:` Не подтверждено, какие поля будут наиболее полезны владельцу
в ежедневной работе. Нужен отдельный review.

## 6. Матрица данных и полномочий

| Data class | Примеры | Хранение в repository | Передача во внешнюю модель | Требование |
|---|---|---|---|---|
| Green | Синтетические templates, публичные ссылки, учебные примеры | Да | Только при необходимости | Минимальный контекст |
| Yellow | Внутренние drafts, рабочие заметки, ограниченная проектная информация | Только при явной политике | Только после отдельного approval | Минимизация и review |
| Red | Secrets, tokens, персональные, финансовые, клиентские или регулируемые данные | Не хранить без отдельного утверждённого механизма | Нет | Local protected storage и отдельная policy |
| Uncertain | Неизвестная чувствительность | Не считать Green до классификации | Нет до классификации | Сначала классификация |

`Decision:` В текущем pilot допускается только Green.

## 7. Суверенность и переносимость

Целевое правило: владелец контролирует данные, модели, контекст и решения.

- Repository содержит только reviewable и намеренно сохранённые артефакты.
- Secrets, tokens и личный профиль не хранятся в Git.
- Внешняя модель получает только минимальный task context.
- Frigga-артефакты остаются переносимыми Markdown-файлами.
- Смена модели/provider не меняет Gate, approval или data policy.
- Защищённое локальное хранилище owner profile требует отдельного Gate,
  threat model и решения владельца.

## 8. Явные ограничения автономности

В текущем и следующем контролируемом контуре запрещено:

- Автоматически определять или переключать Activity, scope, Gate или data class.
- Автоматически собирать персональную модель владельца.
- Менять desktop, системные настройки, файлы или интеграции без команды.
- Выполнять отправку, публикацию, покупку, deployment, Git push, merge,
  удаление или изменение прав без явного approval.
- Передавать Yellow, Red или Uncertain data во внешнюю модель без отдельного
  разрешения.

## 9. RAID-ED additions

| Тип | Описание | Статус | Owner | Следующее действие |
|---|---|---|---|---|
| Assumption | Activity-модель сделает workflow понятнее и безопаснее | Yellow | Владелец repository | Проверить в Gate 1 review |
| Assumption | Шести Activities достаточно для первой модели | Yellow | Владелец repository | Подтвердить или скорректировать |
| Risk | Идея преждевременно превратится в UI/API/automation проект | Yellow | Владелец repository | Сохранить Markdown-only scope |
| Risk | Термин personal model приведёт к хранению чувствительных данных | Yellow | Владелец repository | Не создавать owner profile в Git |
| Evidence gap | Нет evidence о полезности каждого поля состояния | Yellow | Владелец repository | Собрать feedback в review |
| Decision | Принять Activity-модель как future design principle | Yellow | Владелец repository | Решить в Gate 1 |

## 10. Обновлённая рекомендация Gate 1

`Draft recommendation:` утвердить Activity-модель только как **future design
principle** для Control Desk при условиях:

1. Pilot остаётся Green-only и Markdown-only.
2. Не подключаются API, MCP, cloud, UI, automation или deployment.
3. Activities описывают контекст и полномочия, но не запускают действий сами.
4. Owner profile, local protected storage, внешняя модель или интеграция
   потребуют отдельного Gate.
5. Следующим шагом может быть только Level 1 outline и owner feedback.

## 11. Критерии перехода

Переход к Level 1 возможен только когда владелец явно подтвердит:

- Baseline 0 корректен либо скорректирован.
- Activity-модель понятна и не расширяет scope pilot.
- Все work products остаются Green.
- Нет разрешения на API, UI, automation, deployment или реальные данные.
- Разрешено создать только Markdown-only Level 1 outline.
